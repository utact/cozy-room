# AI 활용 기술 문서

**잡아라! 코지 룸** (Grab It! Cozy Room) — 물리 기반 캐주얼 파티 게임

---

## 1. 요약

이 게임은 기획·코드·2D 아트·3D 에셋·인게임 심사 로직까지 **다섯 층위 전부에 생성형 AI를
적용**해 만들었다. 다만 "AI에게 시켜서 나온 것을 그대로 쓴다"가 아니라, **각 층위마다
기계로 검증 가능한 기준을 세우고 그 기준을 통과할 때까지 되돌린다**는 원칙으로 작업했다.
이 문서는 무엇을 어떻게 시켰는지와 함께, **AI 산출물을 어떤 방법으로 검증하고 고쳤는지**를
같은 비중으로 기술한다.

| 층위 | 사용 도구 | 산출물 | 규모 |
|---|---|---|---|
| 개발 전반 | Claude Code (Claude Opus) | 기획 스펙, TypeScript 전체 코드, 자동 검증 | 소스 4,955줄 / 커밋 51개 |
| 3D 캐릭터 | Meshy AI (meshy-5) | 젤리빈 캐릭터 + 리깅 + 애니메이션 4클립 → 8상태 파생 | GLB 1개 |
| 3D 프롭·가구 | Meshy AI (meshy-5) | 프롭 12종, 가구 12종, 크리처 2종 | GLB 26개 |
| 2D 아트 | Higgsfield (nano-banana-pro) | 로고, 키 비주얼 2컷, 리본 배지 | WebP 4개 |
| 인게임 AI 심사위원 | 자체 결정론 엔진 | 태그 가중 채점 + 전용 심사평 72줄 | 외부 API 호출 0 |

전체 에셋 9.3MB. **정적 웹 빌드로 동작하며 런타임 외부 네트워크 요청이 0건이다.** (§6)

## 2. 개발 프로세스에서의 AI 활용 — Claude Code

### 2.1 작업 방식

단순 코드 생성이 아니라 **"명세 → 구현 → 실플레이 검증 → 수정"의 에이전트 루프**로
진행했다. 핵심은 마지막 두 단계다. Claude Code가 Playwright로 게임을 **직접 실행하고,
스크린샷을 보고, 게임 내부 상태를 읽어** 자기 구현을 검증한 뒤 고친다.

```
기획 의도 전달 → 설계 스펙(docs/superpowers/specs/) → 구현
   → 헤드리스 브라우저로 실제 플레이 → 화면·수치 측정 → 기준 미달이면 되돌아감
```

### 2.2 실제로 이 루프가 잡아낸 결함

문서용으로 꾸민 예시가 아니라, **개발 중 이 방식이 아니었으면 그대로 제출됐을 결함들**이다.

**(a) AI 심사가 절반의 맵에서 무의미했던 문제**

캠핑 맵의 질문은 `조명`·`화력`·`조리` 같은 태그에 가중치를 주는데, 정작 바닥에 깔린
12종 프롭 중 그 태그를 가진 물건이 하나도 없었다. 결과적으로 **전원이 기본점 30점 +
난수만 받고 있었다** — 게임의 핵심 훅인 "AI가 채점한다"가 통째로 죽은 상태였다.
화면만 봐서는 점수가 나오니 알 수 없다. 태그 정합성을 기계로 대조해 발견했다.

| 질문 | 수정 전 | 수정 후 |
|---|---|---|
| 한밤중 화장실 갈 때… | 2/9 | (질문 교체) |
| 고기 다 탄다! | 3/8 | (질문 교체) |
| 불멍 타임… | 2/9 | (질문 교체) |
| 텐트에 뭔가 부스럭거린다! | — | **9/9** |
| 캠핑 왔는데 이건 진짜 아니지 않냐? | — | **9/9** |
| 해 지고 급 추워졌다 | — | **9/9** |

교훈을 코드에 남겼다: 질문은 **바닥에 실제로 있는 물건으로 답할 수 있어야 한다.**
지금은 6개 질문 전부 태그 100% 적중을 자동 대조로 확인한다.

**(b) 물건을 집을 때마다 캐릭터가 뛰어오르던 문제**

점프 키가 없는 게임인데 물건을 집으면 캐릭터가 붕 떴다. 원인은 Rapier 임펄스 조인트가
첫 틱에 "떨어져 있는 두 점"을 붙이며 쓴 보정 임펄스의 반작용이었다. 프롭을 손 위치로
먼저 옮긴 뒤 조인트를 걸도록 고쳤다. **가장 무거운 프롭(219kg)으로 측정해 상승량
0.002 단위**(사실상 0)를 확인했다.

**(c) HUD 폭이 화면 절반으로 잘리던 문제**

"누가 무엇을 들었는가"를 보여주는 하단 위젯에서 물건 이름이 `여권·통장 파…`로 잘리고
점수가 두 줄로 접혔다. 자동 너비 절대배치 요소를 `left:50%`로 가운데 정렬해 가용 폭이
**화면의 절반(1440px 중 720px)으로 제한**된 것이 원인이었다. 눈으로는 "좀 좁네"로만
보이는 문제라, 요소 폭을 직접 측정해 확정했다. 이후 6개 해상도(1920×1080 ~ 900×500)에서
잘림 0건·화면 이탈 0건을 자동 확인한다.

**(d) 4인전에서 줄다리기가 통째로 깨져 있던 문제**

같은 물건을 동시에 잡으면 더 세게 버둥거린 쪽이 가져가는 규칙인데, 화면에
`undefined → 3P 뺏었다!` 라는 문구가 떴다. 표시 오류로 보이지만 원인을 따라가면
게임 규칙 자체가 무너져 있었다.

```js
effort: [0, 0]        // 슬롯 2개 — id 2·3인 3P·4P는 자리가 없다
effort[2] += n        // undefined + n = NaN
Math.max(...rolls)    // NaN
indexOf(NaN)          // -1
holders[-1]           // undefined  ← 승자
```

승자가 `undefined`면 `id === winner` 가 아무에게도 맞지 않아, 줄다리기에 참여한
**양쪽 모두**가 물건을 놓쳤다. 2인전에서는 슬롯이 우연히 맞아떨어져 드러나지 않다가
4인전에서만 나타났고, 그마저도 증상이 "가끔 둘 다 놓친다"라 눈으로는 물리 엔진 문제로
오해하기 쉬웠다. 배열을 인원수 길이로 할당해 고쳤고, 같은 유형(고정 길이 배열,
`indexOf` 결과를 그대로 인덱싱)을 전체 소스에서 스캔해 다른 사례가 없음을 확인했다.

**눈에 보이는 증상과 실제 결함의 층위가 다를 수 있다**는 것을 보여주는 사례다. 문구
하나를 고치고 넘어갔다면 규칙이 깨진 채로 제출됐을 것이다.

### 2.3 Claude Code에 준 주요 지시 사항

**(1) 초기 컨셉 전달**

> 2~4인이 흐느적거리는 캐릭터로 물건을 뺏고 던지는 물리 파티 게임. 화면 중앙에 주제가
> 뜨고, 제한 시간이 끝나면 AI가 한 줄 평과 함께 점수를 매긴다. 노트북 한 대를 둘이
> 나눠 쓰는 로컬 멀티플레이가 전제다.

**(2) 폴백 금지 — 이 프로젝트의 핵심 규칙**

> 에셋이 없으면 조용히 프리미티브로 대체하지 말고 에러를 던져라. 폴백이 있으면 화면에
> 실제로 무엇이 렌더링되고 있는지 알 수 없어진다.

이 한 줄이 §6의 CDN 사고를 발견하게 만든 규칙이다. 폴백을 허용했다면 심사위원 초상이
죽은 것도, 로컬 파일이 없는 것도 끝까지 몰랐을 것이다.

**(3) 주석 규칙**

> 결정의 근거를 주석으로 남기되 자명한 내용은 적지 마라. "무엇을 하는가"가 아니라
> "왜 다른 방식이 아니라 이 방식인가"를 적어라.

실제로 생성된 주석:

> 손에 든 물건은 바람을 타지 않는다. 그랩은 조인트로 손에 붙여 두는 방식이라 여기서
> 토크를 걸면 물건이 손 안에서 팽이처럼 돌아 "들고 있다"가 깨진다.

**(4) 검증 지시 — 추측하지 말고 측정하라**

> 눈으로 보고 "괜찮아 보인다"로 끝내지 마라. 브라우저에서 실제로 실행하고, 요소 크기와
> 게임 내부 상태를 숫자로 읽어서 확인해라.

§2.2의 결함 3건이 전부 이 지시에서 나왔다. HUD 문제는 "좀 좁아 보인다"로는 원인을 알 수
없었고, 요소 폭을 실제로 재서야 `left:50%`가 가용 폭을 절반으로 잘랐다는 것이 드러났다.

**(5) 밸런스·연출 판단은 사람이**

줌 인/아웃 연출, 프롭 크기, 이벤트 빈도 같은 체감 요소는 AI가 제안하고 **사람이 실제로
플레이해 보고 채택 여부를 결정**했다. 예를 들어 뺏길 때 카메라를 당겼다 빼는 연출은
구현했다가 "난투 중엔 몇 초에 한 번씩 터져 화면이 계속 들썩이고 내 캐릭터를 놓친다"는
판단으로 걷어냈다. 코드에 그 판단 근거를 주석으로 남겨 두었다.

## 3. 생성형 3D 파이프라인 — Meshy AI

### 3.1 캐릭터

`tools/meshy-characters.mjs` — text-to-3d **preview(지오메트리) → refine(텍스처) → GLB**
3단계를 스크립트로 자동화했다. 리깅·애니메이션은 Meshy의 rig/animate로 이어 붙였다.

실제 사용 프롬프트:

```
Cute jellybean capsule game character, {color} smooth rounded capsule body,
big white oval eyes with black pupils, two tiny stub arms, small flat feet,
no mouth, T-pose friendly for rigging, clean stylized 3D, single character,
game-ready low poly
```

Meshy가 애니메이션마다 GLB를 따로 뱉기 때문에 `tools/merge-character.mjs`가
**walk·pickup·throw·hit 4개를 한 파일로 병합**한다. 게임이 쓰는 상태는 8개
(idle·walk·grab·throw·hit·lobby·win·hold)인데, 부족한 만큼은 **기존 클립의 특정 프레임
구간을 잘라 파생**시켰다. 예를 들어 idle 클립이 없어 pickup 클립에서 캐릭터가 가만히 선
구간을 잘라 재사용했다 — 생성 결과의 부족분을 코드로 메운 사례다.

색상은 에셋을 4벌 만들지 않고 **셰이더 주입으로 런타임 틴팅**해 1개 GLB로 4인을
처리한다(`src/character.ts`). 용량과 로딩 시간을 4분의 1로 줄인다.

### 3.2 프롭·가구

`tools/meshy-props.mjs` — 가구 6종(안락의자·책장·플로어램프·캠핑의자·장작더미·랜턴)을
**병렬로** 생성한다. 순차 실행이면 30분이 넘는데 병렬로 4분 안에 끝난다.

이 6종을 만든 이유가 명확하다. 그 전에는 콘셉트당 가구 GLB가 3종뿐이라 방을 채우려면
같은 소파를 두 번, 같은 아이스박스를 세 번 놓을 수밖에 없었고, **한 화면에 같은 물건이
둘씩 보이면 밀도는 올라가도 "에셋이 모자라 돌려막았다"가 그대로 읽혔다.**

프롬프트에는 스타일 일관성을 위한 공통 접미사를 고정했다:

```
single object, centered, upright, Y-up orientation, resting flat on the ground,
cute stylized 3D game asset, soft matte claymation look, warm cozy palette of
honey wood, cream and amber, clean low poly, no background, no base plate, no text
```

`Y-up`·`resting flat on the ground`를 명시하는 이유가 있다. 게임은 GLB를 바운딩 박스
기준으로 정규화해 **원점을 바닥면 중앙에 맞추는데**(`src/assets.ts`), 모델이 기울거나
누운 채로 나오면 엉뚱한 면을 바닥으로 잡아 물건이 공중에 뜨거나 파묻힌다.
프롬프트 단계에서 막는 것이 후처리보다 싸다.

### 3.3 생성물 후처리 — 텍스처 축소

Meshy가 뱉는 GLB는 개당 2.6~3.8MB인데 그 대부분이 **2048×2048 JPEG 텍스처**다. 화면에서
가구 하나가 차지하는 넓이는 200px 남짓이라 명백한 낭비이고, 웹 게임에서는 첫 로딩이
그만큼 늦어진다.

`@gltf-transform/cli optimize`를 먼저 시도했으나 이 텍스처들에서 vips가
`colourspace: parameter space not set`으로 실패해, **필요한 부분만 직접 처리하는 도구를
작성했다**(`tools/shrink-glb.mjs`). GLB의 JSON/BIN 청크를 파싱해 임베드된 이미지만
1024px WebP로 다시 인코딩하고, 바이트 길이가 바뀌므로 BIN을 다시 쌓으면서 모든
bufferView 오프셋을 새로 적는다.

| 에셋 | 변환 전 | 변환 후 |
|---|---|---|
| armchair | 2,595KB | 448KB |
| bookshelf | 2,893KB | 472KB |
| camp-chair | 3,033KB | 616KB |
| floor-lamp | 2,651KB | 427KB |
| lantern | 3,351KB | 553KB |
| log-pile | 3,832KB | 855KB |
| **합계** | **18.4MB** | **3.3MB** |

82% 감소했고, 게임 화면에서 품질 차이는 보이지 않는다.

### 3.4 생성물과 게임 로직의 분리

**에셋은 비주얼만 담당하고, 물리 콜라이더와 심사용 태그는 코드가 갖는다.**

```
Meshy GLB  →  비주얼 (바운딩 박스 기준 자동 정규화)
카탈로그   →  콜라이더 형태·치수 + 심사 태그 + 밀도
```

GLB에서 convex hull을 뽑는 방식은 액자·리모컨처럼 얇은 물건에서 부정확해져 잡기·던지기
체감이 예측 불가능해진다. 그래서 콜라이더는 손으로 적는다. 덕분에 **에셋을 교체해도
게임 밸런스가 흔들리지 않는다.**

또한 **에셋 부재 시 폴백을 두지 않고 명시적으로 에러를 낸다.** 폴백이 있으면 화면에
실제로 무엇이 렌더링되고 있는지 알 수 없게 되기 때문이다.

## 4. 생성형 2D 아트 — Higgsfield

로고 워드마크, 메뉴·결과 화면 키 비주얼 2컷, 타이틀 리본 배지를 생성했다
(Google nano-banana-pro 모델).

2D 아트의 생성 기준은 **코드에 고정된 UI 팔레트**다. `--night` #191411(방의 그림자),
`--lamp` #f0a94c(스탠드 조명), `--cream` #f7efe4(본문) 세 색이 3D 씬 조명과 콘셉트
정의(`src/themes.ts`)에 그대로 쓰이며, 생성 이미지는 이 팔레트 안에 들어오는 컷만
채택했다. 그래서 타이틀 화면과 인게임 화면이 서로 다른 도구에서 나왔는데도 같은 방의
같은 조명으로 보인다.

**강조색을 하나로 묶은 것이 핵심이다.** 램프색 #f0a94c는 로고 외곽선, 타이머, 심사 패널
제목, 화로대 점광원, HUD 점수까지 전부 같은 값을 쓴다. 생성형 도구를 여러 개 섞어 쓸 때
화면이 흩어지는 것을 막는 가장 싼 방법이었다.

### 4.1 후처리 자동화

`tools/prepare-ui-art.mjs` — 생성 도구가 투명 배경을 만들지 못하고 단색 배경으로 뽑아
주기 때문에, **테두리에서 시작하는 flood fill로 배경을 제거하고 여백을 트림한 뒤 WebP로
변환**한다. 배경이 그림자로 서서히 어두워지는 경우를 위해 배경 판정 허용치를 인자로 뺐다.

키 비주얼은 이 과정에서 PNG 1,410KB → WebP 75KB로 줄었다(약 95% 감소).

AI 심사위원 얼굴은 **의도적으로 생성 이미지를 쓰지 않고 인라인 SVG로 그렸다.** 이유는
다음 절에 있다.

## 5. 인게임 AI 심사위원

### 5.1 구조

```
버저 → JudgePayload { 주제, 플레이어별 제출물(이름 + 태그) }
     → 채점  : 기본점 30 + Σ(물건 태그 × 주제 가중치) + 변덕 ±8  →  0~100
     → 심사평 : 질문 × 물건 전용 문장 (없으면 점수대별 템플릿)
     → JudgeResult { 점수, 한 줄 평 }
```

프롭 12종에는 각각 `소중함`·`소음`·`포근함` 같은 태그가, 질문 6종에는 태그별 가중치가
정의되어 있다. 두 벡터의 내적이 점수가 된다. **외부 API를 호출하지 않으므로 정적 웹
빌드에서 키 없이 항상 동작하고, 심사 지연이 없으며, 심사 결과를 재현할 수 있다.**

### 5.2 심사평을 LLM 호출이 아니라 사전 작성으로 한 이유

초기 구현은 `{item}` 슬롯 하나만 갈아끼우는 범용 템플릿이었다.

> "{item}… 소름 돋았다. 이게 바로 프로의 선택."

어떤 물건을 넣어도 문장이 성립하는데, **어떤 물건을 넣어도 성립한다는 것이 정확히
문제였다.** 웃음은 물건과 상황이 만나는 지점에서 나온다. 층간소음 복수전에 곰인형을
들고 온 것이 웃긴 것이지, 곰인형 자체가 웃긴 것이 아니다.

조합 수가 유한하므로(질문 6 × 프롭 12 = 72) **Claude Code로 72개 조합 전부를 직접
작성**해 `src/verdicts.ts`에 표로 넣었다. 실제 예:

| 질문 | 물건 | 심사평 |
|---|---|---|
| 층간소음 복수전 | 빗자루 | 손잡이로 천장 쿵쿵. 대한민국 표준 복수법이다. 이견 없다. |
| 층간소음 복수전 | 쿠션 | 천장에 던지면 소리 없이 떨어진다. 세상에서 가장 조용한 복수다. |
| 집에 불났다! | 몬스테라 화분 | 무겁고, 크고, 다시 사면 된다. 최악의 3연속이다. |
| 캠핑 왔는데 이건 아니지 | TV 리모컨 | TV는 없는데 리모컨만 챙겼다. 어떤 의미로는 완벽하다. |

이것이 **런타임 LLM 호출보다 나은 선택**인 이유: 지연이 없고, 비용이 0이고, 오프라인에서
동작하고, 품질이 매번 동일하게 보장된다. 파티 게임에서 심사평은 3초 안에 떠야 한다.

표에 칸이 없으면 점수대별 템플릿으로 자연스럽게 폴백하므로, 프롭이나 질문을 추가해도
깨지지 않는다.

### 5.3 AI 봇 — 심사위원과 같은 채점 함수를 공유

심사자가 혼자 평가할 때도 난투가 성립하도록 로컬 로직 AI 봇을 넣었다(`src/bot.ts`).
설계의 핵심은 **봇이 심사위원과 동일한 채점 함수 `scoreProp()`을 호출한다**는 점이다.
기준이 한 함수에서 나오므로 "봇이 좋은 걸 골랐는데 낮은 점수를 받는" 모순이 구조적으로
생기지 않는다.

봇의 행동:

| 상황 | 행동 |
|---|---|
| 빈손 | 점수 ÷ 거리가 가장 높은 프롭으로 |
| 나쁜 걸 들고 있음 | 확실히 더 나은 게 가까이 있으면 갈아탄다 |
| 상대가 더 좋은 걸 들었음 | 그 상대를 노려 던진다 (뺏기 위해서) |
| 남은 시간 6초 이하 + 쓸 만한 물건 | 던지지 않고 상대 반대 방향으로 도망친다 |

봇마다 `aggression` 값이 달라 경합 중인 물건을 노리는 정도가 다르다.

## 6. 런타임 외부 의존 제거

개발 중 UI 아트를 "로컬 우선 → 없으면 생성 계정 CDN" 순서로 로드하는 폴백이 있었다.
제출 직전 점검에서 **로컬 파일 3개가 실제로는 없었고, 게임이 매 실행마다 외부 CDN에서
받아오고 있었으며, 그중 심사위원 초상은 이미 403으로 죽어 있었다**는 것을 네트워크 로그로
확인했다.

계정이 정리되면 제출본이 조용히 깨지는 구조다. 다음과 같이 정리했다:

- 키 비주얼 2컷을 내려받아 WebP로 변환해 저장소에 번들
- 심사위원 얼굴은 인라인 SVG로 다시 그려 이미지 의존 자체를 제거
- CDN 폴백 경로를 코드에서 삭제하고, "URL을 적지 말고 파일을 커밋할 것"을 주석으로 명시

**결과: 게임 실행 시 외부 네트워크 요청 0건.** 오프라인에서도 완전히 동작한다.

## 9. 부록 — 주요 프롬프트 원문

이 프로젝트에서 3D 에셋 프롬프트는 **저장소에 코드로 관리한다.** 문서용으로 옮겨 적은
것이 아니라 `tools/meshy-props.mjs`·`tools/meshy-characters.mjs`에 그대로 들어 있어,
스크립트를 다시 돌리면 같은 방향의 결과가 재현된다. 프롬프트를 소스와 같은 급의 자산으로
다룬다는 뜻이다.

### 9.1 공통 접미사 (가구 6종 전부에 적용)

```
single object, centered, upright, Y-up orientation, resting flat on the ground,
cute stylized 3D game asset, soft matte claymation look, warm cozy palette of
honey wood, cream and amber, clean low poly, no background, no base plate, no text
```

### 9.2 가구별 프롬프트

| 에셋 | 프롬프트 (공통 접미사 앞에 붙는 부분) |
|---|---|
| armchair | A cozy single-seat armchair with plump rounded cushions, warm burnt-orange fabric, short wooden legs, high soft backrest. |
| bookshelf | A low wide wooden bookshelf with two shelves filled with colorful tilted books and a small potted plant on top. |
| floor-lamp | A tall slim floor lamp with a cream fabric drum shade, thin brass stand and a round weighted base, warm glowing bulb. |
| camp-chair | A folding camping chair with taut forest-green fabric seat, black tubular metal frame, cup holder on the armrest. |
| log-pile | A neat stack of chopped firewood logs, cut birch and oak rounds with visible bark and pale end grain, stacked in a low pyramid. |
| lantern | A vintage camping lantern with a glass chamber glowing warm amber, metal cage frame, carry handle on top, standing on a small wooden crate. |

### 9.3 캐릭터 프롬프트

```
Cute jellybean capsule game character, {color} smooth rounded capsule body,
big white oval eyes with black pupils, two tiny stub arms, small flat feet,
no mouth, T-pose friendly for rigging, clean stylized 3D, single character,
game-ready low poly
```

`{color}`에 `warm red-orange (#e4573d)` 등 플레이어 색을 넣는다. 실제로는 이 중 한 벌만
쓰고 나머지 3인은 셰이더 틴팅으로 처리했다(§3.1).

### 9.4 API 파라미터

```js
{ mode: 'preview', art_style: 'realistic', ai_model: 'meshy-5',
  topology: 'quad', target_polycount: 6000 }   // → refine → GLB
```

`target_polycount: 6000`은 가구 기준이다. 화면에서 가구 하나가 200px 남짓을 차지하므로
그 이상은 로딩 시간만 늘린다. `topology: 'quad'`는 후처리 도구와의 호환을 위해 고정했다.

## 10. 한계와 선택

정직하게 밝히는 부분이다.

- **인게임 "AI 심사위원"은 LLM이 아니다.** 태그 가중 채점 + 사전 작성 문장을 쓰는
  결정론적 엔진이다. §5.2에 적은 이유로 의도적으로 택한 구조이며, 런타임 LLM 호출을
  한 것처럼 포장하지 않는다.
- **캠핑 맵은 거실 프롭 12종을 공유한다.** 캠핑 전용 프롭을 따로 만들지 않은 대신,
  질문을 "캠핑장에 이걸 들고 왔다고?" 쪽으로 비틀어 기존 프롭이 웃음의 재료가 되게 했다.
- **생성형 3D의 형태 품질에는 편차가 있다.** 그래서 콜라이더와 태그를 에셋에서 분리해,
  더 나은 에셋으로 교체해도 게임 로직이 영향을 받지 않게 설계했다.
